03 / Collision-engine integration

Connecting collision-query capabilities to an existing engine.

This project extends an existing physics-simulation engine’s collision-query pipeline, connecting additional query capabilities to its geometry representations and interfaces.

MY ROLE

Collision-pipeline extension design, algorithm integration and engine adaptation.

CONTEXT

Research development within an existing physics-simulation engine.

Functional overviewMy contributionConcept illustrationEngineering outcome
01 / Project scope

An engine extension needs more than an isolated algorithm.

The engine’s limited collision-query options needed expansion across broadphase, midphase and narrowphase. New algorithms had to work with the host engine’s existing geometry and stage interfaces.

03 / My contribution

Algorithm capabilities connected to the host engine.

Implemented

Integrated

04 / Engineering considerations

Clear stage responsibilities and compatible interfaces.

Different stages answer different questions

Candidate filtering, spatial hierarchy queries and convex queries operate at different levels. Their results need compatible meanings at stage boundaries.

Extend the engine’s available choices

New query capabilities joined the existing options. Integration made those options usable within the same engine context.

06 / Engineering outcome

Additional collision-query options in the existing engine.

SAP, BVH and GJK became usable query options within the existing engine. The original algorithms, including SAT, remained available alongside the additions.

Technical boundaries

Candidate filtering is conservative, and convex queries have a specific geometric scope. Algorithm suitability depends on the query and scene.

Functional views regroup responsibilities rather than reproduce internal implementation. Animations and illustrative geometry are independently created using synthetic data, not product recordings or measured results.
